CERTIFICATES

Recent certificate incidents and what to check

eMudhra CA key compromise (Oct 2026)

  • Researchers recovered the private keys of 8 eMudhra intermediate CAs. The keys were so weak they could be recovered almost instantly.
  • 6 are TLS CAs: EM DV TLS CA, EM OV TLS CA, EM EV TLS CA, each G3B and G3C, under emSign Root TLS CA - G3.
  • 2 are code-signing CAs: EM OV CS CA - G3B, EM OV CS CA - G3C, under emSign Root CS CA - G3.
  • Blocked by Chrome and Firefox (17 Oct), Apple (19 Oct) and Microsoft (20 Oct). Oracle shipped Java fix CVE-2026-91403.
  • eMudhra says none issued certificates. No exploitation is known, but anyone with the keys could have forged website or code-signing certificates.

DigiCert code-signing theft (April 2026, background)

  • Attackers got into DigiCert's support systems through a malicious file and generated code-signing certificates.
  • Those certificates signed Zhong Stealer malware. DigiCert revoked 60 certificates.
  • Takeaway: a valid signature does not mean a file is safe. Check revocation, not just presence of a signature.

I found no other new certificate attacks this week. A rumor about GoDaddy mass revocation could not be confirmed.

What to check in your organization

  1. Windows certificate stores. Look for emSign / eMudhra intermediates. Windows applies Microsoft's revocation automatically, but servers with updates paused may not have it yet.
  2. Software with its own CA bundle. Java (cacerts), Python (certifi), Node.js, curl/OpenSSL bundles, Docker images and appliances often skip OS revocation. Update Java to the .0.2 builds and refresh certifi and CA bundles.
  3. Your own certificates. If any of your sites or apps use an eMudhra G3 certificate, replace it. eMudhra is reissuing about 30,000 customer certificates under a different root.
  4. Signed executables. Flag any file signed through EM OV CS CA - G3B/G3C. Treat it as suspicious.
  5. Revocation checking. Make sure proxies, EDR and TLS inspection devices check revocation (CRL/OCSP) and don't fail open.
  6. Certificate inventory and expiry. Keep a list of every certificate you own, who issued it and when it expires. Use Certificate Transparency monitoring (e.g. crt.sh) to spot certificates issued for your domains that you didn't request.

Windows: find eMudhra certificates and signed files

# 1. Certificate stores (machine + user): list anything from emSign / eMudhra
Get-ChildItem Cert:\LocalMachine\Root, Cert:\LocalMachine\CA, Cert:\CurrentUser\Root, Cert:\CurrentUser\CA |
  Where-Object { $_.Subject -match 'emSign|eMudhra|EM (DV|OV|EV) TLS CA|EM OV CS CA' -or $_.Issuer -match 'emSign|eMudhra' } |
  Select-Object PSParentPath, Subject, Issuer, Thumbprint, NotAfter | Format-List

# 2. Executables signed through the compromised code-signing CAs (adjust the path)
Get-ChildItem 'C:\Program Files','C:\Program Files (x86)' -Recurse -Include *.exe,*.dll,*.msi -ErrorAction SilentlyContinue |
  Get-AuthenticodeSignature -ErrorAction SilentlyContinue |
  Where-Object { $_.SignerCertificate.Issuer -match 'EM OV CS CA' } |
  Select-Object Path, Status, @{n='Issuer';e={$_.SignerCertificate.Issuer}}

Linux / servers: check a site's chain

# Show the issuer chain served by a host
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null 2>/dev/null \
  | grep -E 's:|i:'

# Look for emSign in the system CA bundle
grep -il emsign /etc/ssl/certs/* 2>/dev/null

Java: check the JDK trust store

# Lists emSign entries in the JDK's cacerts
keytool -list -v -cacerts -storepass changeit | grep -i -A2 emsign

# Confirm the JDK build (want the .0.2 builds)
java -version

A root entry alone is not proof of risk. The fix is the patched JDK, which distrusts the compromised intermediates.
